# Service Rules

- A service is the one place that talks to one outside system: `app/Services/<System>/<System>Service.php`, e.g. `NekoBtService`, `GitHubService`, `VlcBridgeService`. Actions and jobs call it; nothing else sends it requests.
- Its public methods are the questions the app asks (`getTorrents(NekoBtSearchData)`), take DTOs or scalars and return DTOs. URLs, query names, timeouts and parsing stay inside it. When translating the system's answers grows big, that goes in final sibling mapper classes that only the service uses (`NekoBtTorrentMapper`, `NekoBtShowTemplateMapper`); the service keeps the requests and the answer checks.
- Data that is the system's own (a torrent site's listings, its levels and tags) keeps the system's shape: its own DTOs (`App\Dtos\NekoBt`), enums (`NekoBtLevel`), endpoint (`nekobt-torrents`) and resource. Don't force two systems into one shape that fits neither. A shared interface fits only when every system answers in the app's own terms: `ShowTemplateSource` (a show from a page link) is one, implemented by each site's service and registered with `$this->app->tag(...)` in `AppServiceProvider`; `ResolveShowTemplateSourceAction` picks the one for a link. Sources report every title they know, their own first; `GetShowTemplateAction` decides which to keep.
- A system without a usable public API is read from its web pages: the mapper parses the HTML with PHP's `Dom\HTMLDocument` and CSS selectors (`MalShowTemplateMapper`).
- A failure the caller can't fix throws a domain exception that renders its own code (`TorrentSiteUnavailableException('nekobt')`, 502), after a `Log::warning` that says what the system answered.
- Settings of the system (base URL, timeout) live in `config/<system>.php`. A system the user runs themselves, such as their qBittorrent, gets its address and login from settings instead. The service reaches it on its own: `AppServiceProvider` gives it a resolver it calls on first use (so a caller that never sends anything doesn't fail while the system isn't set up), and callers never pass a connection. Checking unsaved values (the setup wizard) is its own method that takes them, `testConnection($values)`. Secrets are `secret` settings, stored encrypted and never sent to the frontend.
- Services are adapters only: no models, actions or HTTP layer classes (`tests/Unit/ArchitectureTest.php`). Caching results and other application policy belong to the calling action. A service that holds state for a run, such as qBittorrent's login session, is bound `scoped` in `AppServiceProvider`, so one request or job shares it.
- Requests go through Saloon (`saloonphp/saloon` with its Laravel plugin), never Laravel's `Http` client (`tests/Unit/ArchitectureTest.php`). Next to the service: `<System>Connector.php` (base URL, auth, headers, `HasTimeout` read from config, `protected ?string $response = LenientJsonResponse::class`) and one `Requests/<Verb><Thing>Request.php` per call (method, endpoint, query or body). Both are `final` and only the service uses them. The service sends with `(new XConnector)->send(new XRequest(...))`, catches `FatalRequestException` for "didn't answer", and checks the answer's status and shape. `LenientJsonResponse` reads a non-JSON body (a bot check's HTML) as no JSON values instead of throwing.
- Tests fake the system with `Saloon::fake([...])`, keyed by connector, request class or URL pattern (`'nekobt.test/*'`), feeding a saved real answer from `tests/Fixtures/<system>/` through `MockResponse::make(...)`, trimmed to the parts the mapper reads and formatted (indented JSON or HTML, never a one-line dump) so a reviewer can read it. `Saloon::fake([])` stops unexpected requests. `tests/Pest.php` has the helpers: `saloonConnectionRefused()`, `saloonSequence([...])`, and `saloonSent()` / `saloonSentUrls()` to check what was sent.
